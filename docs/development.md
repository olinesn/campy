# Development

Running campy's tests, timing tests on a shared machine without spoiling each other's numbers, and how campy's branches and releases work.

## Running the tests
```
pip install -e . pytest pytest-xdist
pytest -n 4 -m "not alone" tests
pytest -m alone tests
```
`-n 4` runs them on 4 workers at once, which takes the suite from about 17 minutes to about 5: most tests wait on real-time recordings (emulated cameras), timers and child processes rather than on the CPU. The second line runs the tests marked `alone`, `bench/rig.py`'s: rig.py looks at the whole machine (every process on it, and its CPU and disk load; on Windows every `python.exe` counts as a GPU user), so beside other tests it would see them as foreign users and wait for them. One `campy-live-view` test is marked `alone` too: it writes frames at 100 fps and checks that the view warns of nothing but the problem it plants, and beside 3 other workers on GitHub's 2-core Windows runner its frame writer was held up past a frame, so its frames really came late. Run in parallel, those tests skip themselves. Plain `pytest tests` still runs everything, on one worker. Each test makes its own files in its own temporary folder and names its own live feed (with its process id), so tests don't depend on each other or on their order; a new test should do the same. `--durations=25` lists the slowest tests.

A few of campy's waits can be shortened through the environment, for tests only, so that a test needn't record for minutes to see them run out: `CAMPY_TEST_LIVE_STALL_S` (campy-watch's 30 s with no result from campy-live before it says campy-live hangs), `CAMPY_TEST_LIVE_STOP_S` (the 30 s campy-session then gives campy-live to stop at its stop file) and `CAMPY_TEST_LIVE_RESTART_S` (how long it waits before starting campy-live again: `10,60,300` s). Nothing else sets them; `tests/test_session.py` does.

GitHub Actions runs them on every push to master or dev and every pull request, on Python 3.9, 3.10 and 3.12 on Linux, Python 3.12 on Windows and Python 3.12 on ARM Linux (`.github/workflows/tests.yml`), each on 4 workers. The RatCam tests need nir-eye-cam's `nireyecam`, from a private repository, and are skipped without it. To run them in CI too, add a repository secret `NIREYECAM_TOKEN`: a fine-grained personal access token with read-only access to the contents of `olinesn/nir-eye-cam`.

The tests run `trigger.ino` as plain C++ against a simulated Arduino. A second workflow (`.github/workflows/sketch.yml`) compiles it for real boards (an Arduino Uno, an Uno R4 Minima, a Nano ESP32, a Teensy 4.0 and a Teensy 3.2) whenever the sketch changes.

## Timing tests on a shared machine (bench/rig.py)
When several people (or several Claude sessions) run recordings, campy-live, replays and benchmarks on one machine, two at once spoil each other's numbers. `bench/rig.py` is a lock they all take, on Linux and on Windows: `run` waits until nobody else holds it and nothing else is on the GPU, the video encoder, the FLIR cameras or the trigger, and the CPU and disk are quiet; then it runs the command, and every 2 s logs anything outside it that touches those to `<tag>.rig.log`, which ends `RIG_CLEAN`, `RIG_CLEAN_BACKGROUND` or `RIG_CONTAMINATED` ([which load counts](#which-load-counts-and-background-programs)). Only numbers from a clean run are worth comparing: trust a run only if the last line of its log starts with `RIG_CLEAN` (with `--strict`, only `RIG_CLEAN` itself). A run stopped before its job ended (Ctrl-C, `kill`, a hangup, an error inside `rig.py`, or on Windows its console window closing, a logoff or a shutdown) ends `RIG_ABORTED` instead, with what was seen until then, and a log with no `RIG_` line at all is from a `rig.py` that was killed outright. Every run whose job started has a log: `rig.py` writes its first line (its version) before it starts the job, so even one killed at that moment leaves a log, with no `RIG_` line.
```
python3 bench/rig.py status
python3 bench/rig.py run <your name> <tag> -- bash my_test.sh <tag> ...
python3 bench/rig.py hold <your name> <tag> <pid>     # for a job already running
python3 bench/rig.py break                            # remove a lock nobody holds any more
```
**The rig stays held for as long as the job runs, however `rig.py` ends.** If `rig.py` is killed outright (`kill -9`, Linux's out-of-memory killer, a tool's time limit), its job goes on, and so does the lock: on Linux, `RIG_BUSY` names the job's process id and start time, and the rig counts as held until that process ends. `rig.py status` then says `rig held: ... (its rig.py has ended, but its job runs on ...)`, the next `rig.py run` waits for the job (and `RIG_BUSY` says who waits), and `rig.py break` refuses. A closed output (`rig.py run ... | head`, or an `ssh` whose local end was cut) doesn't stop `rig.py`: it stops printing and goes on watching and logging to the end. An error inside `rig.py` stops the watch, says so in the log, and keeps the rig until the job ends. `RIG_BUSY` names a run from the moment it has the lock, while it waits for the machine to be quiet too (`... (waiting for the rig to be quiet)`). To keep a run going after the terminal or the `ssh` session closes, start it with `setsid` or `nohup`: a signal that was ignored when `rig.py` started stays ignored, so under `nohup` a hangup stops neither `rig.py` nor its job. **On Windows, closing `rig.py`'s console window** (its X, or Task Manager's End task on the window), a logoff or a shutdown ends the run and frees the rig: Windows ends every program in that window about 5 s later, so `rig.py` ends its job at once (not after the 30 s Ctrl-C allows), logs `RIG_ABORTED by the console window closing` and removes `gpu.lock` in that time. A panel opened with `panel: {rig_lock: auto}` runs under `rig.py`, so closing its window frees the rig too. Only a program ended outright (Task Manager's End process, `taskkill /F`) can't do this; its `gpu.lock` stays, but it counts as free once both of its process ids have ended, and the next `rig.py` removes it.

With an NVIDIA GPU the log also follows the GPU's clock and what holds it down (nvidia-smi's throttle reasons), and the last line gives the median clock. That matters on Windows: the RTX 2000 Ada sat at 780 MHz of its 2,500 during live tracking, and at 210 MHz while waiting for it, until `campy-live` held its clock up.

What it watches:

| | Linux | Windows |
|---|---|---|
| GPU | `/dev/kfd` open; on a Jetson, `/dev/nvgpu/*` or `/dev/nvhost-*gpu` | a CUDA program (type C in `nvidia-smi -q -d PIDS`), or any `python*.exe` |
| Video encoder | `/dev/dri/renderD*` open (CUDA on a Jetson opens it too); on a Jetson, `/dev/v4l2-nvenc` | `ffmpeg*.exe` |
| FLIR cameras | their USB devices open, or Spinnaker loaded | a Spinnaker DLL loaded |
| Trigger | `/dev/ttyACM*`, `/dev/ttyUSB*` open | a COM port open |
| Desktop on the GPU (noted, not waited for) | gnome-shell, Xwayland, Xorg, and a logged-in GNOME session's gsd-xsettings, mutter-x11-frames and desktop portals (GNOME's portal helper opens the GPU with the first dialog it draws and keeps it until it ends); GNOME Software's background service and the first-login wizard, which keep the GPU open on a Jetson's desktop, ...; one starting or ending contaminates the run | programs that draw on the GPU (dwm.exe, explorer.exe, ...); Windows starts and ends some by itself, so this is only logged |

On Windows, every Python process counts as a GPU user, because any of them may start CUDA (`nvidia-smi` lists a CUDA program only once it has). The disk load there starts from what all the physical disks actually read and wrote (the `PhysicalDisk(_Total)` counter): what processes outside the job read and wrote, but no more than the disks moved, since Windows counts a process's pipes, devices, network and cached files alike; or, if more, what the disks moved beyond the job's own reads and writes, which catches a file copy that went into Windows' memory cache and was written out after the copy had ended. The kernel's own count ("System", pid 4) is left out: Windows' display driver charges it with every frame a job copies to the GPU, 400-800 MB/s on the Precision 7875 with nothing read from or written to a disk, which made every GPU benchmark there end `RIG_CONTAMINATED` before. The lock there is a file, `C:\campy_data\live\gpu.lock`, created only if it is absent, and deleted when the run ends. It names who holds the rig and since when, and the process ids of `rig.py` and of the job: once both have ended, the lock counts as free, so a crash can't leave the rig locked. A `gpu.lock` written by hand (a name and a time) holds the rig until whoever wrote it deletes it, or `rig.py break`.

A script takes the lock by itself when its first command is `. <folder of rig.py>/rig_guard.sh "$@"` (bash), or, in PowerShell, `. <folder of rig.py>\rig_guard.ps1 @args; if ($null -ne $RigExit) { exit $RigExit }`. `RIG_OWNER` names who runs it; on Windows `RIG_PYTHON` names the `python.exe` to run `rig.py` with. It needs only Python's standard library, and is installed by copying, not with campy: the machines run the copy in their lock's folder, not the one in a campy checkout. On the lab's EVO-X2 that is `~/sleap-bench` (`RIG_ROOT`), where `rig.sh` runs `rig.py` with `/usr/bin/python3`; on the Windows machines (the Dell Pro Max Slim FCS1250 and the Dell Precision 7875), `C:\campy_data\live`, with `RIG_PYTHON` set as a user environment variable to a 64-bit Python 3.9 or newer. Each machine runs that one installed copy, never a checkout's: a checkout may be on any branch or commit, and every lock user on a machine must run the same lock.

**Which version a machine runs.** The lock's version is a short hash of its six files (`rig.py`, `rig_windows.py`, `rig_guard.sh`, `rig_guard.ps1`, `rig_hold.ps1`, `rig_banner.ps1`), with line endings ignored (Windows checkouts have `\r\n`), so one commit shows the same version on every machine. `rig.py version` prints it, and `rig.py status` gives it on its second line, after `rig held` or `rig free`, and with when, from which campy commit and by whom it was installed (`rig.py 3f826b121d in C:\campy_data\live, installed 2026-11-05 10:12:03 from campy 2825003 by <you>`); a copy edited by hand since says so. Every `<tag>.rig.log` has the same line before `rig held by`, and a run started from a checkout's `rig.py` says there whether that copy is the installed one.

**Updating it: `rig.py install`, run from the new checkout.** After a change to these files is merged into `dev` (or with a release), update a campy checkout on the machine, then run that checkout's own copy: `python <checkout>/bench/rig.py install --owner <you>` (on Linux `/usr/bin/python3`; on Windows the `RIG_PYTHON` one). It takes the rig without waiting, so it exits 75 and changes nothing if anyone holds it (a run, a `rig_hold.ps1` window), or if any other `rig.py run`, `hold` or `install`, or `rig_hold.ps1`, is running or waiting for the rig: a waiting `rig.py` has loaded the old code and would start on a mix. Otherwise it copies the old files to `rig-backup/<old version>-<date>-<time>/` in the lock's folder, writes each new file beside the old one, reads it back, renames it into place (a rename is all or nothing, so nothing ever sees half a file), checks the installed version, and records what it did in `RIG_INSTALLED` and `rig-install.log` there. It refuses a checkout with uncommitted changes to the six files (`--allow-dirty`) or one older than the installed commit (`--allow-older`). Files copied out of a checkout (a folder that isn't a git checkout) can name their commit with `--commit <commit>`, for `RIG_INSTALLED` to show. `--check` only compares: it lists each file as same, differs or new, and exits 0 when the installed copy is the checkout's and 3 when it isn't. Inside the rig's own job, as in an update script run under `rig.py run`, it doesn't wait for the rig that job holds. Since it is itself a Python program, start it only once the lock file shows the rig free, checked without Python: on Linux `flock -n -s <folder>/.rig.lock true` succeeds and `pgrep -f "[r]ig.py (run|hold)"` finds nothing; on Windows there is no `gpu.lock`. On a held rig any Python counts as a foreign GPU user in the running test. To go back, copy the files from the backup folder over the installed ones the same way, with the rig free.

**Release updates.** The update scripts that move a rig's checkout to a new release or to `dev` run under `rig.py run` already; they should end with `<python> <checkout>/bench/rig.py install --check`, which says when the installed lock differs from the checkout's. Installing stays a step of its own, done when the machine is free.

**Holding a Windows machine for your own work.** Training a model, or anything else long that uses the GPU, would spoil a timing test, and a test would slow down your work. To keep tests off the machine meanwhile, run `bench/rig_hold.ps1` at the machine (or over Remote Desktop) and leave its window open:
```
powershell -NoProfile -ExecutionPolicy Bypass -File C:\campy_data\live\rig_hold.ps1 -Owner <you> -Tag <what, e.g. sleap-training> -Why "<one line>"
```
A `.bat` file holding that line makes it a double-click. It writes `gpu.lock` as `rig.py` does, naming its own window as the holder, so `rig.py status` says `rig held: <you> <what> since <time> ... (held at the screen with rig_hold.ps1: <one line>; ...)`, and every `rig.py run`, guarded script and `rig.py hold` waits; `rig.py break` refuses to remove it. If a test holds the machine when you start it, it waits for that test to end and says so. It starts and stops nothing else, and needs no Python, so it can't count as a GPU user itself. To end the hold, press R then Y in its window, which deletes the lock and says RELEASED; or close the window: `rig.py` counts a lock whose holder has ended as free. The window's title says WAITING, HELD (with the time held) or RELEASED, and what it prints goes to a `.log` beside the script. It is for Windows only; on Linux, `rig.py hold <you> <what> <pid>` holds the machine for as long as a program you started runs.

**Experiment machines: tests only when nobody is there, and one click stops them.** A machine people record experiments on (the Dell Pro Tower Plus) gets stricter rules, switched on by an `experiment.json` in the lock's folder. There `rig.py run` starts a test only when all of these hold, and otherwise exits 75 at once, saying why (it never waits in line):
- every Windows session has been idle for 15 minutes or more (`quser`; a machine nobody is logged on to counts as idle);
- nothing else uses the GPU, a camera, the video encoder or the trigger (no campy, no SpinView, no Python), and the CPU and disk are quiet, as everywhere;
- the hour is allowed: `"hours": "22:00-06:00"`, nights only, is the default;
- tests aren't paused: there is no `PAUSE` file in the lock's folder, or its time has passed;
- on Windows, the banner (`bench/rig_banner.ps1`) runs in the session and has shown the test. `rig.py` starts it through its Task Scheduler task when it isn't running, and starts the test only once the banner says it shows it.

The banner is an orange strip at the top of the screen, at the machine or over Remote Desktop, on top of every window but never taking the keyboard: `campy test running: <tag> (by <who>, since 11:40 PM). Touching the mouse or keyboard stops it. [Stop test]`. It is PowerShell, not Python, since `rig.py` counts every `python.exe` as a GPU user. It is hidden while nothing runs. A test is stopped, every process of it within 2 s, by any of:
- a click on **Stop test**, or the desktop shortcut **Stop campy test**;
- any keyboard or mouse input in the session while the test runs;
- unlocking the screen, a Remote Desktop connect (on Windows 11 it takes over the session at the screen), or a logon;
- anything starting to use the GPU, a camera, the encoder or the trigger outside the test (campy, SpinView, a camera opened), which `rig.py` itself sees;
- `quser` showing a new session, a session that changed state, or a session whose idle time went back down.

The banner (or the shortcut) writes a `STOP` file in the lock's folder, and that is all it does: it ends no process itself and needs no rights. `rig.py` looks for `STOP` every 0.2 s, ends the test's Windows job object, logs `RIG_STOPPED at the machine by <how>` as the log's last line, and exits 75. Every stop also writes `PAUSE`: no new test starts until 9 AM the next morning (`"pause_until"`). The banner then says `Stopped (<how>). The machine is yours. No new campy tests until 9:00 AM tomorrow.` and offers **Pause 2 hours instead** and **Pause until resumed**. The desktop shortcut **Resume campy tests** removes `PAUSE`. A stopped test is not a failure and not a timing result: don't rerun it until the machine is free again. Tests there never use the real cameras: rig checks run emulated cameras and recorded replays only. `rig.py status` shows the experiment machine's state: its hours, whether tests are paused, whether the banner runs, and each session's idle time.

To set a machine up, install the lock as usual (`rig.py install`), then, as the lab account, run `powershell -NoProfile -ExecutionPolicy Bypass -File bench\rig_experiment_setup.ps1` (`-Hours`, `-IdleMinutes`, `-PauseUntil` to change the defaults). It writes `experiment.json`, registers the Task Scheduler task `campy test banner` (it starts the banner at logon, in the lab account's own session), puts the two shortcuts on the desktop and starts the banner. It needs no admin rights. `-Undo` removes all of it. What the banner does goes to `rig_banner.log` in the lock's folder.

**Remote desktop on a Linux test machine (Sunshine and Moonlight).** The GMKtec EVO-X2 (Ubuntu 24.04, GNOME on Wayland) can be used from another computer with [Sunshine](https://github.com/LizardByte/Sunshine) on the machine and [Moonlight](https://moonlight-stream.org/) on the computer you sit at. How it is set up there, and what it means for tests:

- **Sunshine runs all the time, as the logged-in user.** It is the `.deb` from Sunshine's GitHub releases for Ubuntu 24.04 (2026.914.233613, checksum checked). It captures the screen straight from the GPU (`capture = kms`) and encodes it with VA-API on the integrated GPU (`encoder = vaapi`). Moonlight on an M2 Mac picks H.265. The machine logs in by itself at boot, so there is always a desktop to show, and Sunshine starts with it (`systemctl --user enable sunshine`).
- **Idle, it doesn't touch the GPU.** With nobody connected, Sunshine has no GPU device open and uses no measurable CPU. `rig.py status` doesn't list it, and smoke1 gave the same result with Sunshine running and with it stopped (1,800 sets, 0 skipped, inference 3.0/3.1 ms p50/p99, the 2.4.0 baseline).
- **Streaming, it is an encoder user, and the lock treats it as one.** While someone is connected, Sunshine has the GPU's video encoder open: a test waits for the stream to end, and a stream that starts during a test makes it `RIG_CONTAMINATED`. So check `rig.py status` before connecting, and don't connect during a test.
- **A logged-in desktop is on the GPU all the time.** Each run's last line names it (`desktop on the GPU: ...`), so compare timing runs only with the same desktop note. GNOME's `gsd-xsettings` and `mutter-x11-frames` keep the GPU's render node open for as long as someone is logged in; `rig.py` counts them as desktop. So does GNOME's portal helper, `xdg-desktop-portal-gnome`, which draws the dialogs apps ask the desktop for (a file chooser, the screen-sharing picker): it opens the render node with the first dialog it draws and keeps it until it ends. A lock from before pull request 401 counts it as an outside encoder user instead: on 11 November it opened the render node partway through one run, and the next run waited for it until it was stopped (`systemctl --user stop xdg-desktop-portal-gnome.service`). Since 401 the note also names the portal programs that are running (`xdg-desktop-portal` itself and its `-gnome` and `-gtk` helpers, whose names the kernel cuts to the same 15 characters), so it can be longer than an older run's note on the same desktop. On the EVO-X2, with nobody streaming, the logged-in desktop didn't change smoke1's numbers.
- **Two settings that aren't obvious.** Sunshine's web page refuses a login from another computer (`CSRF Protection Error`) until its address is in `csrf_allowed_origins` in `sunshine.conf`, for example `https://<machine's address>:47990`. Sunshine's sample apps "Low Res Desktop" (which runs `xrandr` on an HDMI output) and "Steam Big Picture" don't apply to a Wayland test machine; `apps.json` keeps only "Desktop".
- **Updates, now that someone is logged in.** A logged-in Ubuntu desktop runs the update notifier, which pops up windows and checks for updates in the background; it is off for the rig's account (a per-user autostart override). Ubuntu's automatic updates (`unattended-upgrades`) install security and regular Ubuntu fixes, but skip a run while the rig lock is busy: a small check that only reads the lock, set as `ExecCondition=` on `apt-daily.service` and `apt-daily-upgrade.service`, so the timer tries again next time. GPU firmware and drivers (`linux-firmware*`, Mesa, `libdrm`, `libgbm`, `libva`) are on the automatic updater's `Package-Blacklist`, since they can change GPU timing; a daily check says when some wait (a `campy-notify` Slack message and a desktop notification), so they are installed on purpose, followed by a restart and a smoke1. Third-party sources (ROCm, Docker, Tailscale, TeamViewer) stay manual; TeamViewer's update can switch its background service back on, which spoiled tests before.
- **Pairing:** Moonlight shows a PIN; enter it on Sunshine's web page (`https://<machine's address>:47990`, PIN tab). The web page's username and password are made by whoever sets it up, at their first visit.

### Which load counts, and background programs
One look at anything outside the run on the GPU, the encoder, a camera or the trigger, a desktop starting or ending on Linux, or the lock changed by someone else contaminates the run. CPU and disk load outside the run is different, because most machines have programs that nobody can stop and that wake up now and then. On the Windows PCs that is the IT security agent: as a test starts it often reads 70–110 MB/s or uses 1–3 cores for a few seconds, above the limits of 2 cores and 50 MB/s, while the test's times match clean runs to within 0.1 ms. Before 13 November 2026 one such look contaminated the run, so most runs on those PCs had to be repeated. Now:

- **Load has to last.** Every look above `--cpu` or `--io` is still logged as a `LOAD` line, but it contaminates the run only when it lasts 2 looks in a row (`--load-looks`, `RIG_LOAD_LOOKS`) or comes in more than a fifth of the run's looks (`--load-share 0.2`, `RIG_LOAD_SHARE`). A shorter burst leaves the run `RIG_CLEAN (brief load outside the job in 1 of 30 looks, longest 1 look (2 s) in a row, peak 2.3 cores, 70 MB/s (not counted: ...))`.
- **A machine can list its background programs** in `background.json` in the lock's folder (`~/sleap-bench` or `C:\campy_data\live`), each with the most CPU and disk it may use. Load from them, within those ceilings, is taken out before the limits are applied, and `run` doesn't wait for it. A run in which only listed programs took the load over the limits ends `RIG_CLEAN_BACKGROUND (background (background.json) above the limits in 3 of 30 looks, longest 2 looks (4 s) in a row: <program> peak 2.6 cores, 108 MB/s)`. That holds for at most a quarter of the run's looks, or 3 looks for a short run (`"share"` and `"looks"` in the file): in the 2.5.0 round, the Pro Max Slim's 1-camera run had a p99 of 7.8 ms against 2.4 ms, with the scanner seen through its second half, so background through much of a run still makes it `RIG_CONTAMINATED`. A listed program above its ceiling counts like any other program (the `LOAD` line says `ABOVE its ceiling`).
- **`--strict`** (or `RIG_STRICT=1`, which guarded scripts pass on) restores the old rule: every look above the limits contaminates the run, and `background.json` is not read. Use it for a script that must have a machine with nothing else running; check that its log ends exactly `RIG_CLEAN`.

`RIG_CLEAN_BACKGROUND` starts with `RIG_CLEAN`, so a script that looks for `RIG_CLEAN` at the start of the last line accepts it; one that wants a run with no background at all looks for `RIG_CLEAN` followed by a space or the end of the line, or runs with `--strict`. The log's second line says which rules the run used and lists the background programs, and `rig.py status` marks a listed program `[background: ...]` in its load list.
```
{"processes": [
   {"name": "agent.exe", "cpu": 4, "io": 200, "why": "IT security agent"},
   {"path": "C:/Program Files/Vendor/*/scanner.exe", "cpu": 4, "io": 200}],
 "share": 0.25, "looks": 3}
```
Choosing entries:
- **Name the program by its file, or better by its full path.** `"name"` is the program's file name (on Windows the image name `rig.py status` shows; on Linux the command's first word); `"path"` is the whole path, which another program can't take by being named the same. `*` and `?` match anything, and letter case doesn't matter. On Windows the path comes from the program's command line, so a program started without its full path can only be listed by name; one whose command line can't be read is never excused by its path. An agent whose command line can be read only some of the time (it happened in a quarter of the looks on the Pro Max Slim) needs both: its folder by `"path"` first (the first entry that matches is the one used), then its main program by `"name"`.
- **List only programs that run on the machine all the time and that you can't stop**: the IT security agent, the operating system's own services. Never list campy, Python, ffmpeg, a browser, a backup or a file copy, or anything a person starts: that load is exactly what the lock is there to catch.
- **Set each ceiling from what the program was seen doing, with some room**, from the `LOAD` lines of earlier runs or from `rig.py status`. All of an entry's processes count together against its ceiling, so an agent's main service and its workers can share one entry (a folder with `*`). On Windows a program's own count is all its reads and writes, including the network and what is served from memory (one agent's reached 6,102 MB/s while the disks moved a few), so `rig.py` compares at most what the disks moved with the ceiling.
- **What the security agent did on the three Dell PCs** (13 November 2026, from every rig log since 21 October; a log has at most one `LOAD` line every 30 s, naming the 3 busiest programs, so real peaks can be somewhat higher). The agent's main service and its workers together, in the looks where the load went over the limits, since 1 November:

  | | Looks | Cores: typical / 90th percentile / most | Disk, MB/s: 90th percentile / most |
  |---|---|---|---|
  | Dell Precision 7875 | 25 | 1.6 / 2.0 / 2.8 | 134 / 140 |
  | Dell Pro Max Slim FCS1250 | 57 | 0.8 / 1.5 / 2.9 | 79 / 107 |
  | Dell Pro Tower Plus | 50 | 1.2 / 1.9 / 2.5 | 94 / 171 |
  | Windows 11 VM (8 virtual cores, since 21 October) | 21 | 1.0 / 1.4 / 2.3 | 1 / 68 |

  Once more, on the Pro Tower Plus, it read 499 MB/s; in October, on the Precision 7875, it used up to 6.8 cores while TensorRT engines were built. So 4 cores and 200 MB/s for the agent covers every look since 1 November with some room, and still counts the larger bursts. Replayed on the rig checks marked `RIG_CONTAMINATED` since 1 November, with those ceilings (counting only the logged looks, so a little hopeful), 13 of 15 would have been clean (10 by the new duration rule alone) on the Precision 7875, 17 of 24 on the Pro Max Slim and 18 of 20 on the Pro Tower Plus. The Windows 11 VM, whose agent stayed lower, got 3 cores and 100 MB/s, and 10 of its 14 would have been clean.
- **Some disk load belongs to no program.** Many sightings on these PCs are disks moving 55–130 MB/s with no program outside the run charged for it: 31 since 21 October on the Pro Max Slim, 8 on the Pro Tower Plus, 7 on the Precision 7875. Most likely these are reads that Windows doesn't charge to any program: a scanner's driver reading files from inside the kernel, or a program mapping large libraries (torch and CUDA) into memory, the run's own included. No entry can excuse that load; only the duration rule lets a short burst of it pass. The 2.5.0 run above, slowed by the agent, was mostly this kind, and would still be `RIG_CONTAMINATED`. The 1-camera rig checks on these PCs see such load in 20–31% of their looks, around the quarter allowed for background. A disk trace on the Pro Max Slim and the Windows 11 VM (13 November, Windows' own recorder `wpr` with disk events only, kept in memory so that it adds no disk load, around a 1-camera check) showed two things. Windows writes a run's own recording to the disk later, from its file cache, and charges that to the kernel (`System`), not to the run. On the Pro Max Slim, reads of the new recording were also charged to the kernel, probably the security agent reading it, and the agent wrote about 3 MB to its own databases. The disks moved at most 2.3 MB/s in any second, though: the bursts of 55–130 MB/s did not come during the traced runs, nor in that morning's checks. In the logs they came mostly in the first checks after an update. A trace armed for the first check after the next one (campy `e1f3d35`, 13 November 10:06 AM, on the three Dell PCs) found no burst there either: no second above 20 MB/s, mostly NTFS's own records of the new files, the recording and the agent's hash database (16 MB on the Precision 7875). So, for an update that changes only Python files, the bursts are not the agent reading them the first time they are loaded; what they are is still open. A trace written to the disk as it records (`wpr -filemode`) is no use for this: its own writes, and the shadow-copy writes they cause, were most of what it measured.
- **Change the file only while the rig is free**, as with other changes in the lock's folder; it is read when a run starts, and it is not part of the lock's version. A file that can't be read, or an entry without a program or both ceilings, excuses nothing, and the log says so.

## Development and releases
Everything lands on `dev` first. `master` is the released campy, and changes only when `dev` is promoted to it.

- **Pull requests** go to `dev`, the repository's default branch.
- **Trying `dev` on a rig:** in its clone, `git fetch`, `git checkout dev` and `git pull`; `git checkout master` goes back. The code is current as soon as the branch is checked out, because `pip install -e .` runs it from the clone. But `pip show campy` keeps the version from the last `pip install -e .`, so to have it report the checked-out version, run `pip install -e . --no-deps` with the campy environment active (`--no-deps` leaves the other packages alone; without it, pip may also update dependencies). Run a full `pip install -e .` when `setup.py`'s dependencies changed.
- **A pre-release** marks a state of `dev` to test, for example on the rigs. Set `version` in `setup.py` to it (`2.1.0rc1`) in a pull request to `dev`, so a rig reports that version once it has run `pip install -e . --no-deps` on it, then:
  ```
  gh release create v2.1.0rc1 --target dev --prerelease --generate-notes
  ```
  Pre-release tags take Python's form, `v2.1.0rc1`, `v2.1.0rc2`, ..., which pip orders before `2.1.0`. A rig checks one out with `git checkout v2.1.0rc1`.
- **A release:** set `version` in `setup.py` to it (`2.1.0`) in a pull request to `dev`. Then run **Actions ▸ Promote dev to master ▸ Run workflow** with the tag `v2.1.0`, or:
  ```
  gh workflow run promote.yml -f tag=v2.1.0
  ```
  It moves `master` forward to `dev` and publishes release `v2.1.0` on that commit, with notes listing the pull requests merged since the last release. With no tag it only promotes. It changes nothing if `setup.py`'s version is not the tag's, or if `master` has a commit that `dev` lacks: promotion only ever fast-forwards, because merging or squashing `dev` into `master` would leave the two histories apart, and every later promotion would conflict.
